# ds 沙箱






简单讲述一下这篇论文理解，

先简答讲述一下对强化学习的理解

我们在 sft 中，是人工做的语料，高质量语料， 主要是用来做 能力对齐，安全对齐，但是人力毕竟有限，所以 rl 这种无监督学习 被用来训练llm，并且在实践中发现，llm 还可以通过自己的探索，提升llm 的性能。

但是 随之而来也有了新的问题，无监督学习，怎么计算损失的，之前无论是预训练 还是 sft ，都是一种监督学习， llm 这种的预测下一个的 token 的函数，强化学习只有一个问题，是没有回答的。

一个很容易想到的策略就是，通过  预训练和 sft ，模型已经有了一些基本解决问题的能力，一个问题，让这个模型去执行多次，拿到多个回答，我们称之为  rollout，每个回答就是一个训练样本，但是问题是我们不知道应不应该采纳这个建议。

所以还需要训练一个奖励模型，奖励模型给这几个回答打分，我们简单理解一下，就是先按照    rollout 来正常计算的  损失，然后在根据奖励模型的分数 来重新矫正的 损失。

在交叉熵中，我们希望的损失最小，然后计算出一个数值，这个数值的越大 说明越偏离实际，

   2. 写代码

然后是 llm 在回答这个的问题的时候，对周围的环境有什么要求

1. 隔离型

   1. 不能自己写了一个代码，把别人干碎了
2. 资源敏感性

   1. 因 任务类型而定

      1. 比如 让 她 刷lc，没有性能需求，一般符合复杂度都可以跑出来
      2. 但是某些 性能优化的设计，受环境的影响很大
3. 最少资源满足

   1. 比如 codex  的 compute use，大模型就需要视觉能力，你的 环境就需要gpu
   2. 写 gpu 算子，你的环境就需要 gpu
   3. 但是你要是写业务代码，给个cpu 就行
   4. 如果是 写 算法类的，提供一个 oj 接口就可以，就像刷 lc 一样，本地写代码，然后提交代码，由oj 来打分，那么 对于这种任务 ，环境的话，就是一个接口

我们会看到不同的任务 对 环境的需求是不一样的，所以 ds 提供了4 中的容器环境

1. Serverless

   1. 你可以任务就是 api 调用，给你一个接口，你直接调用就可以了

   1. 虚拟化的一种，我们开发一般都用这种，灵活，方便

   5. [The Hugging Face incident and the road ahead | OpenAI](https://openai.com/index/hugging-face-incident-and-the-road-ahead/)   openai 今年发生的事情，就是用 docker ，导致逃逸了

   1. 也是虚拟机，
   2. micro vm 主要虚拟化 计算资源，但是一般是没有的  gui 的，那么 compute use 就无法使用

2. 内存资源

   1. 真正可以回收的大头
   2. linux 内核 的 内存分配策略就是狠狠用，你给多少我就用多少的，page cache 狠狠用

      1. ![image](https://pic.bynshard.top/image-20261007114149-f1j0osw.png)
      2. 黄色的就是 page cache 的占用，绿色是当前实际在使用
      3. 这是有一定历史原因的

         1. 早期机械磁盘很慢，如果每次读取文件，都要从磁盘读取，然后放到内存，端到端的时间太长
         2. 所以 linux 内核就把每次的读取到的文件数据，放到的内存中，一般程序访问都有局部性，这些文件很有可能再次用到，这样端到端的时间就会变少
      4. 等到内存不足了，我会回收这部分文件页，
      5. 但是这在的  rl 中就很不行了

         1. 我们一般按照波峰来分配的内存的， 这导致我给你分配这么多 ，结果 全用来缓存page cache 了，并且一直占用，
         2. 所以我们需要有一些感知的手段，来主动回收

            1. 不多做介绍，气球模型，psi，你就知道，我们有一种手段，可以把当前的 沙箱中  这部分的回收，
            2. 云服务商，为了超卖，这些方案也都弄过，可以直接拿过来借鉴，这个是阿里云的方案

               1. ![image](https://pic.bynshard.top/image-20261007115207-srreggt.png)
            3. ds 这篇论文，主要是把这技术缝到一起了，然后做了端到端的的工程落地
   3. micro vm 需要解决的一个问题

      1. 这个对于没有基础的人可能有点难
      2. 我们刚才说了 pagecache ，linux 内核默认的策略就是 就是缓存文件访问
      3. 那么 对于符合  virtio  协议的磁盘，它会缓存多份

         1. ![image](https://pic.bynshard.top/image-20261007120951-0s8ybbw.png)
         2. 这个问题，linux 中应该有了解决访问，不在使用 virtio 抽象的磁盘，抽象成  Virtio Pmem

            1. Pmem 是一种 可以用 内存语义访问的存储介质，linux 内核对这种介质是不缓存 page cache ，并且兼容  vfs 的调用
            2. 本质就是个 糊裱匠 ，有啥问题，就复用复用先跑起来再说，本质是linux  内核早期的技术债的爆发
            3. [VirtIO Persistent Memory — QEMU documentation](https://www.qemu.org/docs/master/system/devices/virtio/virtio-pmem.html)

3. 磁盘资源

   1. 这个本质上 不是沙箱在运行时，因为运行时的沙箱磁盘几乎无法回收

         /bin/bash

         Layer 3: COPY hello.txt
         ────────────────────────────
         /app/hello.txt

         Layer 4: RUN echo ...
         ────────────────────────────
         /app/info.txt
         ```
      2. ```cpp
         lowerdir（镜像，只读）
         ────────────────────────
         /app/hello.txt = hello v1


         upperdir（当前容器，可写）
         ────────────────────────
         /app/hello.txt = hello v2


                 ↓ OverlayFS 合并


         merged（容器看到的）
         ────────────────────────
         /app/hello.txt = hello v2
         ```
